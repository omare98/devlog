PR마다 CI가 7분쯤 걸렸습니다. 프론트엔드 글자 하나만 고쳐도 백엔드 전체 테스트를 기다리는 구조였고, 시간이 가장 많이 드는 곳은 늘 백엔드였습니다.

## 바뀐 파일을 보고 정하기

CI 맨 앞에 `changes` 작업을 두었습니다. PR의 기준 커밋과 마지막 커밋 사이에서 바뀐 파일 목록을 뽑아 백엔드, 쇼핑몰, 관리자 중 무엇이 바뀌었는지 판단합니다. `main`에 올라가는 푸시는 항상 전부 검사합니다. 워크플로 파일이나 스크립트가 바뀌면 전부 확인합니다.

작업 이름이 바뀌면 브랜치 보호 같은 곳에서 필수 검사 이름이 어긋날 수 있어서, 프론트엔드 작업은 이름을 그대로 두고 **안쪽 단계만 건너뜁니다**. 프론트가 안 바뀐 PR에서는 그 작업이 4초 만에 끝납니다.

같은 PR에 새 커밋을 올리면 이전 실행은 취소하도록 해서 쌓이는 실행도 줄였습니다.

## 처음에 잘못 말한 것

첫 PR에서 "백엔드는 건너뛴다"고 말했는데 실제로는 백엔드가 돌았습니다. 번역 파일(`admin/src/i18n/locales`)을 고쳤기 때문입니다. 서버 테스트 가운데 `ErrorDetailTranslationTest` 하나가 두 앱의 번역 파일을 읽어 서버 오류 문구와 맞는지 확인하는데, 번역이 어긋나면 그 테스트가 잡아야 하므로 돌리는 게 맞았습니다. 제가 설명을 잘못한 것이고 동작은 의도대로였습니다.

## 번역만 바뀐 PR은 더 줄이기

그래도 번역 한 줄 때문에 전체 백엔드를 기다리는 건 아까웠습니다. 번역 파일만 바뀐 PR은 전체 대신 **그 테스트 하나만** 돌리게 했습니다. 서버 코드가 함께 바뀌면 전체를 돌립니다.

## 지금의 모습

| 바뀐 것 | 돌아가는 검사 |
|---|---|
| 백엔드 코드 | 백엔드 전체(7분 안팎) |
| 번역 파일만 | 번역 일치 테스트 하나 |
| 프론트엔드만 | 해당 앱(2분 안팎) |
| `main` 푸시 | 전부 |

## 남은 것

백엔드 코드가 바뀌면 여전히 7분 정도 걸립니다. 더 줄이려면 테스트를 병렬로 돌려야 하는데, 테스트가 같은 DB를 공유해서 DB를 나누는 작업이 필요합니다. 동시성 테스트와 부딪힐 수 있어 신중히 하려고 미뤄 두었습니다. 먼저 어떤 테스트가 오래 걸리는지 측정하는 것이 순서일 것 같습니다.

## 배운 것

- 건너뛰는 규칙은 **무엇이 안 돌아가는지**를 정확히 말할 수 있어야 합니다. 대충 설명하면 나중에 신뢰가 깨집니다.
- 검사의 이름은 약속이라서, 줄이더라도 이름은 그대로 둡니다.
