CI에서 `sessionsFromLoginsRacingResetNeverSurvive`라는 테스트가 가끔 빨갛게 실패했습니다. 로그인 여섯 개 스레드가 비밀번호 재설정과 동시에 부딪히게 만든 테스트이고, 실패 원인은 MariaDB 교착(deadlock)이었습니다. 이번에는 "또 그 테스트네" 하고 다시 돌리는 대신 원인을 끝까지 찾았습니다.

## 먼저 내 변경 때문인지부터

그 PR은 워크플로 파일만 바꿨습니다. 같은 테스트가 하루 전 `main`에서도 같은 이유로 실패한 기록이 있어서, 내 변경과 무관한 기존 문제로 정리할 수 있었습니다. 다만 운영에서도 생길 수 있는 문제일 수 있으니 따로 조사하기로 했습니다.

## 실패 기록이 알려 준 것

CI 로그에는 `BatchUpdateException`이 있었습니다. 이 서비스의 로그인 흐름에서 배치로 INSERT 하는 곳은 Spring Session이 응답을 마치며 세션 속성을 저장하는 부분뿐입니다. 로그인 코드는 이미 교착 재시도(`RetryingTransaction`) 안에 있었는데, 이 저장은 그 바깥이라 재시도되지 않고 곧바로 500이 됩니다.

## 로컬에서는 재현되지 않았다

테스트를 로컬에서 여덟 번 돌려도 통과했고, 로그인 48건씩 60라운드를 도는 별도 시도에서도 교착은 0건이었습니다. 느린 CI 서버에서만 타이밍이 겹치는 듯했습니다. 여기서 "재시도부터 붙이자"로 가면 오류만 가릴 뿐이라, 타이밍에 기대지 않고 **잠금 순서를 직접 만들기**로 했습니다.

## 순환의 모양

- 비밀번호 재설정은 `DELETE FROM spring_session WHERE PRINCIPAL_NAME = ?`로 그 회원의 세션을 지웁니다. 외래 키 CASCADE로 속성 행도 같이 지워지고, 이때 인덱스 구간에 gap 잠금이 걸립니다.
- 로그인은 세션 행을 넣은 다음 속성 행을 넣습니다.
- 로그인이 세션 행을 넣고 멈춘 사이 삭제가 끼어들면, 삭제는 로그인이 넣은 행을 기다립니다. 그런데 로그인의 속성 키가 삭제가 잠근 구간 안에 있으면 로그인도 삭제를 기다립니다. 서로 기다리는 순환입니다.

세션 키가 무작위 UUID라서 새 키가 옛 키보다 **뒤에** 놓일 때만 이렇게 됩니다. 그래서 가끔만 실패합니다.

## 두 연결로 만들어 보기

옛 세션 하나를 넣어 두고, 연결 두 개로 위 순서를 그대로 실행했습니다.

| 새 세션 키의 위치 | 결과 |
|---|---|
| 옛 키보다 뒤 | 로그인의 속성 INSERT가 `Deadlock found`로 실패 |
| 옛 키보다 앞 | 둘 다 성공 |

실패하는 쪽과 성공하는 쪽이 가설대로 갈렸으니 원인이 확인된 것으로 봤습니다.

## 고치기

삭제가 인덱스 구간을 훑으니 문제였습니다. 그래서 `PRIMARY_ID`만 **잠금 없이 읽고, 키로 한 건씩** 지우게 바꿨습니다. 삭제가 로그인이 방금 넣은 행을 기다리지 않으니 순환이 생기지 않습니다. 읽은 뒤에 새로 생긴 세션은 지우지 못하지만, 비밀번호가 바뀌면서 자격 증명 스탬프가 달라져 다음 요청에서 거부됩니다. 기존 테스트가 이미 이 동작을 검증합니다.

회귀 테스트는 위 두 연결 시나리오를 그대로 옮겼습니다. 고치기 전에는 교착으로 실패했고, 고친 뒤에는 통과합니다. 관리자 쪽 세션 삭제는 처음부터 세션 ID 단위라 같은 문제가 없었습니다.

## 배운 것

- **재현되지 않는 동시성 문제는 순서를 만들어서 재현합니다.** 타이밍을 맞추려고 반복하는 것보다 확실합니다.
- 오류 종류(`BatchUpdateException`)가 어느 코드 경로인지 알려 주는 단서가 됩니다.
- 재시도는 마지막 수단입니다. 원인이 잠금 순서라면 순서를 바꾸는 편이 낫습니다.
- 고친 뒤에도 원래 간헐 실패 테스트가 로컬에서 실패한 적은 없습니다. 그래서 확인은 결정적 재현 테스트와 전체 테스트 통과로 했고, 앞으로 CI에서 다시 안 나는지 지켜볼 것입니다.
