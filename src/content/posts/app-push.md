구매대행은 주문이 손님 모르게 멈추기 쉽습니다. 특히 배송비를 따로 내는 주문은 관리자가 배송비를 정해도 손님이 결제하지 않으면 그 자리에서 멈춥니다. 그래서 안드로이드 앱에 주문 상태 알림을 넣었습니다. 알림은 구글의 FCM(무료)으로 보냅니다.

## 범위: 거래 알림만, 관리자가 한 일만

- 안드로이드 앱에만 보냅니다. 아이폰과 브라우저 웹 푸시는 하지 않습니다.
- 구매 시작, 배송비 결제 요청, 배송 시작, 배송 완료, 취소 다섯 가지만 보냅니다. 광고성 알림은 동의를 따로 받아야 해서 넣지 않았습니다.
- **관리자가 바꾼 상태에서만** 만듭니다. 손님이 직접 한 결제나 취소는 이미 화면에서 아니까 보내지 않습니다.
- 잠금 화면에 보일 수 있어서 알림 문구에는 주문번호와 상태 안내만 넣고, 금액·이름·주소는 넣지 않습니다. 문구는 손님이 쓰는 언어 네 가지로 나갑니다.

## 구조: 알림 행을 같은 트랜잭션에 저장하고, 보내는 일은 따로

관리자가 상태를 바꾸는 **같은 트랜잭션**에서 `push_notifications` 행을 `PENDING`으로 저장합니다. 별도 발송기가 이 행을 읽어 FCM으로 보내고 결과를 같은 행에 기록합니다. 이 행이 발송 대기열이면서 관리자 "알림 내역"의 원본입니다.

- 상태 변경이 롤백되면 알림 행도 없습니다. 보내지 않을 알림이 남지 않습니다.
- 주문번호와 상태 조합에 유일 키를 둬서, 같은 알림은 한 번만 만들어집니다. 배송비를 다시 확정해도 알림이 또 가지 않습니다.
- 서버가 둘(관리자, 상점)이라 둘 다 발송기를 돌립니다. 행을 가져갈 때 `FOR UPDATE SKIP LOCKED`로 한쪽만 집어 가게 합니다.
- 실패하면 30초, 5분 뒤 다시 시도하고 세 번째 실패에서 `FAILED`로 끝냅니다. 건너뛴 경우(손님이 꺼 둠, 등록된 기기 없음, 서버에 FCM 설정 없음)도 이유와 함께 남겨서 "알림이 안 왔다"는 문의에 답할 수 있게 했습니다.
- 키가 없어도 서버는 정상으로 뜨고, 그때 알림은 "푸시 설정 없음"으로만 남습니다. 개발 PC에서 키 없이도 돌아야 했습니다.

## 리뷰가 잡아 준 것: FCM 응답을 기다리는 동안 DB 행을 잡고 있었다

처음에는 행을 가져가서 FCM에 보내고 결과를 기록하는 일을 한 트랜잭션에 넣었습니다. 전체 브랜치를 새 눈으로 리뷰받자 두 가지가 나왔습니다.

- Firebase SDK의 기본 연결·읽기 제한 시간은 **무제한**입니다. FCM이 느리면 그동안 그 행의 잠금과 DB 연결을 붙잡습니다.
- 관리자가 같은 주문의 배송비를 다시 확정하면 알림 저장이 그 잠긴 행을 기다리다 잠금 대기 시간이 지나 **주문 처리가 오류로 끝날 수 있습니다.** "알림 발송이 주문 처리를 늦추면 안 된다"는 이번 작업의 핵심 규칙을 깨는 구조였습니다.

고친 방법입니다.

1. 행을 가져가는 짧은 트랜잭션에서 다음 시도 시각을 2분 뒤로 미뤄 둡니다(임대). 그다음 **FCM 호출은 트랜잭션 밖에서** 하고, 결과는 또 다른 짧은 트랜잭션으로 기록합니다. 보내는 중 서버가 죽으면 행은 `PENDING`으로 남아 임대가 끝난 뒤 다시 처리됩니다(전달은 "한 번 이상").
2. FCM 연결·읽기 제한 시간을 5초, 10초로 직접 지정했습니다.
3. 알림 행을 저장할 때 이미 있는지를 **잠금 없이** 먼저 읽어 보고, 있으면 아무것도 하지 않습니다. 발송기가 그 행을 잠그고 있어도 기다리지 않습니다.

이 세 가지는 각각 먼저 실패하는 테스트로 고정했습니다. 테스트 하나는 발송기가 FCM 응답을 기다리는 동안 다른 연결에서 그 행을 `FOR UPDATE NOWAIT`로 잠가 보는 것이고, 잠기면 바로 실패합니다.

같은 리뷰에서 실패 사유가 한국어 문장으로 저장되고 있었다는 것도 나왔습니다. 관리자가 영어나 중국어로 쓰면 한국어가 그대로 보입니다. 사유를 언어와 상관없는 코드로 저장하고 관리자 화면에서 번역하도록 바꿨습니다. 코드가 모르는 값이면 코드 그대로 보여 줍니다.

## 앱 쪽에서 만난 함정: Capacitor 플러그인을 `await`하면 조용히 실패한다

앱은 웹을 서버에서 불러오는 Capacitor 껍데기라서, 푸시 코드는 상점 웹 안에 있고 브라우저에서는 아무것도 하지 않아야 합니다. 앱 안에서만 플러그인을 동적으로 불러 쓰도록 했는데, 테스트가 처음에 `"PushNotifications" plugin is not implemented`로 실패했습니다.

원인은 Capacitor 플러그인 객체가 **어떤 속성을 읽어도 메서드처럼 돌려준다**는 점입니다. 플러그인을 `await`하거나 `async` 함수의 반환값으로 넘기면 JavaScript가 `then` 속성을 확인하는데, 이것이 플러그인 메서드 호출로 바뀌어 "구현되지 않음"으로 실패합니다. 제 코드는 이 실패를 `catch`로 삼키고 있었어서, 테스트가 없었다면 **실제 앱에서 푸시가 조용히 안 됐을 겁니다.** 플러그인을 객체에 담아 돌려주고 구조 분해로 꺼내도록 고쳤습니다.

같은 테스트에서 하나가 더 나왔습니다. 알림 누름 감지와 기기 등록, 두 곳이 거의 동시에 플러그인을 동적으로 불러오면 한쪽이 다른 모듈을 받는 경쟁이 있었습니다. 불러오기를 한 번만 하고 결과를 나눠 쓰도록 했습니다.

알림을 눌렀을 때 열 주소는 서버가 보낸 값이지만 그대로 믿지 않습니다. 같은 사이트의 `/{언어}/orders/{주문번호}` 모양만 열고, 외부 주소나 `//호스트`, `..` 같은 값은 무시합니다.

## 실제 폰에서 만난 문제 두 가지

**1. 폰에서만 로그인이 안 됐습니다.** PC에서는 되는데 폰 앱에서는 안 됐고, 서버 보안 로그에는 로그인 성공이 찍혔습니다. 원인은 서버가 내려 주는 XSRF 쿠키와 세션 쿠키가 항상 `Secure`라는 점이었습니다. 브라우저는 `localhost`가 아닌 `http` 주소에서는 Secure 쿠키를 저장하지 않습니다. 폰이 PC의 사설 주소로 접속하면 로그인이 성공해도 폰은 로그인 상태를 잃습니다. `Secure` 표시를 설정으로 분리했고 **기본값은 그대로 켜 둬서 운영은 영향이 없습니다.** 개발 PC의 로컬 설정에서만 끕니다. 기본값과 끈 값을 각각 테스트로 확인했습니다.

**2. 안드로이드 17에서 상단이 가려졌습니다.** 시계와 배터리가 로고 위에 겹치고, 아래 탭이 제스처 바와 겹쳤습니다. 안드로이드 15부터 앱 화면이 시스템 바 아래까지 그려지는데, 설정으로 켜 둔 Capacitor의 자동 여백 옵션이 이 폰(안드로이드 17)에서는 작동하지 않았습니다. 앱 시작 화면에서 시스템 바, 노치, 키보드 높이만큼 직접 여백을 주도록 했습니다. 이 수정은 에뮬레이터 없이 실제 폰으로만 확인할 수 있었습니다.

개발 PC에서 안드로이드 빌드가 JDK 25로 실패하는 일도 있었습니다. 안드로이드 Gradle은 JDK 17 또는 21이 필요한데, Android Studio에 들어 있는 JDK가 25로 바뀌어 있었습니다. 따로 설치된 JDK 21로 빌드하고 문서를 고쳤습니다.

## 남긴 것

- 기기 수 제한이 없고 쓸모없는 토큰은 정리되지 않습니다. 오류 코드 `INVALID_ARGUMENT`는 우리 쪽 내용 오류일 수도 있어서 기기를 지우지 않기로 했습니다.
- 세션 만료나 계정 정지로 풀린 로그아웃에서는 그 폰이 알림 대상에 남습니다.
- 앱이 열려 있는 동안에는 안드로이드가 알림을 띄우지 않습니다.
- 앱 안의 구글 로그인은 아직 없습니다. 구글이 앱 내장 브라우저와 사설 IP 주소를 막아서 앱 전용 로그인이 따로 필요합니다.
