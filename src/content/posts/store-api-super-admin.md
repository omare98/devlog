관리자 메뉴를 정리하면서 사이트 설정·약관·금지어·코드 관리를 "슈퍼 관리자 전용" 그룹으로 옮겼습니다. 화면에서는 일반 관리자에게 그 메뉴가 보이지 않고, 권한표에서도 "상점관리" 행을 없앴습니다. 그런데 **서버는 여전히 예전 `STORE` 권한을 확인하고 있었습니다.**

## 구멍은 화면 밖에 있었다

화면을 막는 것과 API를 막는 것은 다릅니다. 예전에 `STORE` 권한을 받은 일반 관리자 역할이 DB에 남아 있으면, 그 관리자는 화면에 메뉴가 없어도 `PUT /api/settings/...`를 직접 호출해 사이트 설정을 바꿀 수 있었습니다. 권한표에서 행을 지웠기 때문에 **주는 방법은 없는데 이미 준 것은 남아 있는** 상태였습니다. 개발 데이터뿐이라 당장 피해는 없지만, 운영에 가기 전에 반드시 막아야 하는 종류의 문제입니다.

문서에도 "서버에서 아직 STORE 권한을 확인하므로 예전 권한이 남아 있다"고 적어 두고 후속 작업으로 미뤄 둔 항목이었습니다.

## 고치는 것 자체는 단순하다

`@RequirePermission(menu = Menu.STORE, action = ...)`이 붙은 엔드포인트 14개를 `@RequireSuperAdmin`으로 바꿨습니다. 사이트 설정, 약관, 금지어, 코드 이름 수정·만들기·삭제가 대상입니다. 카테고리·상품 읽기 API에 붙어 있던 `orMenus = { STORE, ... }` 예외에서도 STORE를 뺐습니다.

일부러 건드리지 않은 것도 있습니다.

- **`GET /api/codes`**: 화면의 상태 이름(결제 완료, 배송 중 등)을 보여 주려고 모든 관리자가 읽습니다. 로그인만 있으면 되는 API로 그대로 둡니다.
- **`Menu.STORE` 값**: 권한 행이 DB에 남아 있어서 값 자체를 지우면 읽다가 깨질 수 있습니다. 쓰는 곳만 없앴습니다.

## 테스트가 진짜 일을 했다

이 작업에서 중요한 것은 고치는 코드가 아니라 **빠짐없이 막혔는지 확인하는 테스트**였습니다. 새 테스트 `StoreApisSuperAdminOnlyTest`는 14개 요청을 목록으로 들고, 세 종류의 관리자로 모두 호출합니다.

- 권한이 아무것도 없는 관리자: 모두 403
- 예전 STORE 권한을 전부(조회·등록·수정·삭제) 가진 관리자: 모두 403
- 슈퍼 관리자: 401도 403도 아님(본문이 비어 400이 나와도 상관없음)

권한 검사는 컨트롤러 인자를 읽기 전에 인터셉터에서 일어납니다. 그래서 요청 본문은 `{}`만 보내도 403 여부를 정확히 볼 수 있습니다. 구현 전에 돌려 보니 "예전 STORE 권한 관리자" 테스트만 실패했습니다. 구멍이 실제로 있었다는 증거입니다.

잠근 뒤 관리자 서버 테스트를 전부 돌리니 기존 테스트 8개가 실패했습니다. 일반 관리자에게 STORE 권한을 주고 "성공해야 한다"고 확인하던 테스트들이라, 새 규칙에 맞게 "STORE 전체 권한도 403, 슈퍼 관리자는 성공"으로 고쳤습니다. 이름도 `...IsSuperAdminOnlyEvenWithAFullLegacyStorePermission`처럼 바꿔 의도를 드러냈습니다.

## 남은 것

- 권한 행이 DB에 남은 역할은 화면에서 지울 방법이 없습니다. 운영 전에는 마이그레이션으로 STORE 권한 행을 정리하는 편이 깔끔합니다(지금은 어떤 API도 이 행을 읽지 않아 안전합니다).
- 메뉴를 옮길 때는 **화면, 서버 권한, 테스트, 문서**를 같은 변경에서 함께 바꿔야 합니다. 이번에는 메뉴 정리와 서버 잠금이 두 번에 나뉘면서 그 사이에 구멍이 있었습니다.
